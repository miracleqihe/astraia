误提交或误操作后，先不要急着重置、强推或清理。确认工作区、暂存区、提交历史及远程分支分别处于什么状态，并保全未提交内容；已共享的历史通常优先考虑不改写历史的更正方式。泄露密钥时先撤销或轮换，再按托管平台的完整流程处理历史和其他副本。

**定义：** Git 的撤销可能针对工作区文件、暂存区或已经创建的提交；这三种状态不同。历史重写会生成新的提交对象和标识，使用旧历史的协作者及远程引用都可能受影响。


同样叫“撤销”，取消暂存、保留改动地移动分支，以及丢弃工作区改动的后果完全不同。先确认改动存在哪里，才能选择对应方法，减少把尚未备份的工作一起丢掉的风险。

**机制 / 关键点**


| 操作 | 主要影响 | 容易忽略的边界 |
|---|---|---|
| 查看 `git status`、`git diff`、`git diff --cached` | 分别查看状态、工作区与暂存区差异、暂存区与提交差异 | 查看不会恢复任何内容；未跟踪文件也要另行保全。 |
| `git reset --soft HEAD~1` | 将当前分支移动到上一提交，通常保留暂存区与工作区状态 | 须确有父提交并确认只改自己的本地历史；它不会消除远程已有副本。 |
| `git reset --hard` | 将索引及跟踪文件工作区重置到目标提交 | 未提交改动可能丢失，必要时也可能覆盖未跟踪文件；reflog 记录引用移动，不能保证恢复从未提交的工作区内容。 |
| `git revert` | 产生一个新的反向提交 | 适合某些共享历史的更正，但合并提交和冲突需具体处理，不会抹掉旧历史。 |
| 重写历史及强制推送 | 修改提交标识及远程引用 | 可能覆盖他人工作；`--force-with-lease` 有检查前提，并非完整协作保护方案。 |

reflog 默认的普通记录过期阈值是 90 天，不可从当前引用到达的记录默认是 30 天；配置和清理时机可能不同。只有记录仍存在且相关对象仍可取得时，才可能找回先前引用指向的提交，不能把它当成备份。

**可操作安全步骤**


1. 在正确仓库中依次查看 `git status --short`、`git diff`、`git diff --cached`、`git log --oneline -n 10` 和 `git reflog -n 20`。其中普通 diff 主要比较工作区与暂存区，带 `--cached` 的 diff 比较暂存区与当前提交。
2. 按数据敏感性和项目规则备份需要保留的工作区、暂存内容及相关引用；镜像仓库主要保存 Git 引用和对象，不能代替未提交文件的备份。记录当前分支、提交及远程状态。
3. 先区分问题：若只是暂存了不该暂存的文件，查阅适用 Git 版本的 `git restore --staged`；若只是本地最后一次提交需要调整，在确认父提交及保全内容后再选择适当操作；若已经共享，先考虑通过新提交更正并与协作者协调。
4. 若敏感凭据已进入历史，先撤销或轮换凭据，并按照安全事件流程评估权限、日志和通知。历史清理要核对所有相关引用、分叉、他人克隆、托管平台缓存及拉取请求等；重写并强推一次不能保证所有副本消失。
5. 处理后对照预期核验工作区、暂存区、提交、远程引用及协作者恢复情况；复杂操作先在隔离副本中演练。

**可核对的例子：** 例如某个错误提交已经被同事拉取：先保存尚未提交的文件，再查看该提交的影响范围；若决定以反向提交更正，普通提交可在确认提交标识后用 `git revert <提交>`，冲突按仓库流程解决。合并提交需要明确主线父提交，不能照搬普通提交的处理；撤销提交也不会消除已泄露的密钥。

**常见误区**


- “删除当前文件并再提交，就删除了所有历史”：旧提交或其他副本仍可能保留数据。
- “reflog 可以恢复任何内容”：从未提交的工作区改动可能无法从 reflog 恢复。
- “`--force-with-lease` 保证没有协作风险”：它只能在指定条件下检查远程引用，不会替代备份和协商。
- “重写并强推后，泄露凭据就安全”：凭据应及时失效，历史副本、缓存和分叉仍需按平台流程处理。

**边界 / 何时求助专业人士：** 共享仓库、受保护分支、签名、子模块、合规保全或泄露事件应由仓库负责人和相应安全人员共同评估；本文不假定任何清理方式适用于所有平台或仓库状态。

**注意：** 来源包含 Git 官方操作文档及 GitHub 的敏感数据移除指南；命令选项、托管行为和组织流程应核对当前版本。对于可能丢失的数据，先验证备份，再进行不可逆操作。
